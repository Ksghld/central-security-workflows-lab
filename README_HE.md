# מעבדת בקרות קוד מאובטח

זוהי מעבדה סינתטית בלבד. אין פריסה לענן ואין שימוש בנתוני ארגון אמיתיים.
כל הרצות GitHub משתמשות ב־ubuntu-latest. קוד היישום נקרא כמידע בלבד.

## תהליך העבודה

1. מנהל מורשה יוצר את שני המאגרים ומאשר את הרשאות האינטגרציה הקיימת.
2. עובדים בענף תכונה מבודד דרך הכלים המאושרים. אין ליצור אמצעי הזדהות חדש.
3. Push מפעיל ניטור. ממצא סינתטי אינו מבטל Push שכבר התקבל.
4. פתיחת PR או עדכון שלו מפעילים אימות מרכזי במצב enforce.
5. אדם מורשה בודק וממזג. הסוכן אינו ממזג ואינו דוחף ישירות ל־main.
6. אחרי המיזוג בודקים שהראיות מתייחסות ל־SHA שהגיע בפועל ל־main.

## אימות מקומי

```bash
python -m pytest -q tests
python scripts/evidence.py fixtures/coverage.json reports
```

הדוחות נוצרים בפורמטים JSON, Markdown ו־CSV. תוצאה UNKNOWN אומרת שאין
ראיות מספיקות. אין להפוך אותה ל־PASS. בדיקות מקומיות אינן הוכחת אכיפה מרוחקת.

## בעלות וגבול אמון

היישום מצהיר על זהות ובעלות בקובץ application.json. הרשימה המאושרת נמצאת
במאגר המרכזי. שינוי הצהרת הבעלות ב־PR אינו משנה את הרשימה המרכזית.
הזהות כוללת מזהה מאגר ציבורי אמיתי שכבר נקשר לרישום המרכזי. שמות השירות,
הצוות ורשומות הפריסה נשארים נתוני דוגמה סינתטיים ולא מקור ארגוני מוסמך.

יש להבחין בין PR Head SHA, קומיט הבדיקה המשולב של GitHub, וקומיט המיזוג
שהגיע ל־main. הצלחה ישנה אינה מאמתת קומיט חדש.

מנהל מגדיר Ruleset פעיל עבור ענף היעד main בלבד, דרישת PR, חסימת מחיקה
ו־force push, ואת שם הבדיקה המדויק שנצפה ב־Checks API עם מקור GitHub Actions.
אין להניח ששם הבדיקה זהה לשם ה־caller: workflow משותף עשוי ליצור שם מורכב.
נדרשת ביקורת עצמאית כאשר קיים בודק מורשה נוסף. אין לטעון שנבדקה ביקורת
ארבע עיניים בלי שני חשבונות עצמאיים.

תוקף שיכול לשנות את ה־caller יכול להחליפו בפקודה שמצליחה באותו שם.
המעבדה כוללת הדגמה מקומית לכך, אך לא ניסוי עקיפה מרוחק. מקור GitHub Actions
אינו מוכיח שקוד הבדיקה לא שונה. בסביבת ייצור נדרשת סמכות אימות עצמאית.
